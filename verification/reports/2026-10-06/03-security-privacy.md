> 읽는 법: 모든 지적에 `docs/파일:줄`과 원문 인용을 붙였다. 자동 검증(00-scripts.txt)이 이미 통과한 본문 정화 XSS 32개·DDL 제약·Lua·동시성은 다시 확인하지 않았고, **본문이 아닌 출력 지점**과 **인증·인가의 빈틈**에 집중했다. 결정 기록에 이유가 적힌 결정(예: 비공개 글 사진은 주소를 알면 보임, 탈퇴 후 handle 영구 보존)은 "다르게 하자"고 지적하지 않았고, 다른 결정·보안 요구와 충돌하는 경우만 적었다.

## 발견 사항

### [높음] 프록시 뒤에서 "IP"가 무엇인지 정하지 않아 IP 기반 제한이 전부 묶이거나 위조된다 (A12)
- **위치:** docs/07-auth.md:18 ("같은 IP는 1분에 20회"), docs/07-auth.md:90 ("같은 IP 1시간에 20번"), docs/07-auth.md:125, docs/08-blog-address.md:112 ("같은 IP 1분에 30번"), docs/09-nickname.md:111, docs/31-view-count.md:31 (`h:{SHA-256(IP + User-Agent + 오늘의 비밀값)}`), docs/33-search.md:131 (31과 같은 방문자 키), docs/02-architecture.md:10-35 (구조도: `브라우저 -->|HTTPS| APP`, 프록시·로드밸런서 없음), verification/prompts/common.md:60 ("운영 환경(서버 2대, …)")
- **문제:** IP를 키로 쓰는 제한이 5곳, 조회수 방문자 해시가 1곳인데, 서버가 어떤 값을 "IP"로 보는지(리버스 프록시·로드밸런서 뒤에서 `X-Forwarded-For`를 신뢰할지, 몇 홉까지, 어떤 설정으로)가 어느 문서에도 없다. 서버 2대면 앞에 반드시 프록시가 있다.
- **영향:** (a) 프록시 뒤에서 remote address를 그대로 쓰면 모든 사용자가 프록시 IP 하나로 묶인다 → 전체 사용자가 로그인 "1분 20회"를 공유해 21번째 로그인부터 전부 429, 비밀번호 재설정은 1시간에 20명만 가능, 쿠키 없는 방문자의 조회수가 전부 한 사람으로 합산된다. (b) 반대로 `X-Forwarded-For`를 검증 없이 믿으면 공격자가 헤더 값을 바꿔 가며 로그인 IP 제한·재설정 제한·중복 확인 제한을 전부 우회하고(계정별 5회 잠금만 남음), 조회수 해시 키도 마음대로 만들어 조회수를 부풀린다.
- **제안:** 02 §5 또는 07 §6에 "신뢰하는 프록시 홉 수와 Spring `server.forward-headers-strategy`(또는 `ForwardedHeaderFilter`) 설정, 그 밖의 출처가 보낸 `X-Forwarded-For`는 무시"를 적고, 모든 IP 키는 이 값을 쓴다고 명시. 완료 기준에 "위조한 `X-Forwarded-For`로 제한을 우회하지 못한다"를 추가.
- **담당:** 02·07 공통 (키를 쓰는 08·09 공통, 31·33 김민서는 참조만)
- **확신:** 확실

### [높음] Q2에서 JWT를 고르면 "정지·탈퇴·비밀번호 변경 시 모든 세션 즉시 삭제"가 성립하지 않는다 (A6)
- **위치:** docs/07-auth.md:123 ("JWT를 쓰는 팀원은 Refresh 토큰을 Redis에 저장하고 재발급할 때마다 교체"), docs/02-architecture.md:17 ("세션 또는 JWT — 각자 선택"), docs/01-common-requirements.md:104 (Q2 미결). 즉시 무효화를 요구하는 곳: docs/07-auth.md:84,174 ("그 계정의 모든 세션 삭제"), docs/11-profile.md:174, docs/13-delete-withdraw.md:112,200, docs/42-permission-matrix.md:20,251 ("정지하면 그 회원의 모든 세션이 즉시 끊기고"), docs/43-report-hide.md:160,196
- **문제:** 5개 문서가 "모든 세션 즉시 삭제"를 완료 기준으로 삼는데, JWT 쪽 규칙은 Refresh 토큰 교체 한 줄뿐이다. access token 수명·저장 위치·폐기 목록(denylist)이 없으면 access token은 만료까지 유효하다. 세션 고정 방지(docs/07-auth.md:128)도 세션 전용 규칙이다.
- **영향:** JWT를 고른 팀원이 문서대로 구현하면 정지된 회원·탈퇴 신청한 회원·비밀번호를 바꾼(= 탈취를 의심한) 회원의 기존 access token으로 글·댓글·좋아요 쓰기가 만료까지 계속된다. 42 §12 4-1, 07 §9 5, 13 §5 1, 43 §8 8이 JWT 경로에서는 거짓이 된다.
- **제안:** 07 §6에 JWT 조건부 규칙을 추가: access 수명 ≤ 10분 + 쿠키(HttpOnly) 저장 고정 + 정지·탈퇴·비밀번호 변경·재설정 시 `member.token_version` 증가(또는 Redis `auth:revoked:{memberId}` = 시각)를 모든 요청에서 확인. 또는 Q2를 "SSR + Spring Session"으로 확정해 JWT 문장을 삭제.
- **담당:** 07 공통 (Q2 회의 안건)
- **확신:** 확실

## 부록 B. docs/42-permission-matrix.md와 다른 칸·빠진 행

**42와 다른 칸 (문서끼리 모순):**
1. 자기 글 좋아요: 42:22 `400` ↔ 30:60,184 `403` (+ 판정 순서 42:49-58 ↔ 30:36-44). 42:290-291에 "요청"으로만 남음.
2. AI 태그 추천 남의 글: 42 P-4 `404` ↔ 34:290 `403`.
3. 태그 자동완성 비회원: 42:204 `✓` ↔ 22:215 `로그인 필요`.
4. 관리자 전용 주소 비회원: 42:155 `401` ↔ 42:23 P-10 "존재도 드러내지 않음(404)".
5. 작성자의 임시글 상세: 42:92 `✅ 배지` ↔ 40:17 `302 에디터`.
6. 숨긴 글의 관리자 열람: 42:94 `✅ (관리자 화면)` ↔ 43:93 `스냅샷만`.
7. 인증 전 회원 정의: 42:34 `이메일 가입만` ↔ 07:112 `GitHub 이메일 없으면 다시 인증`.
8. 댓글 작성 판정 순서: 42:49-58 ↔ 21:131-139 (400·429 위치).

**42에 빠진 행 (근거가 다른 문서에만 있거나 아예 없음):**
- 계정: 회원 가입, 로그인·로그아웃, 이메일 인증·재발송, 비밀번호 찾기·재설정, 중복 확인 API, `POST /api/me/restore`, `GET /api/me/storage`, **관리자 지정·해제(A1)**.
- 글: 에디터 열기 `/write/{id}`, `POST /api/markdown/preview`(인증 전 칸 없음), **AI 태그 추천**, 검색(글·사람·블로그 안), 트렌딩, sitemap·RSS, 조회 기록 API.
- 사진: `complete`·`content`의 소유자 조건, 본문 이미지 업로더 조건.
- 친구 공개 규격 전체(요청·수락·거절·취소·끊기·목록)와 **친구 열** — 06 §8은 친구 열을 요구(06:207)하지만 42에는 없음.
- 정지 회원 열 — 42:38이 의도적으로 생략했으나 "비밀번호 재설정 ✓"(42:174)처럼 비회원과 다른 칸이 실제로 있고, 이메일 인증 링크·소셜 콜백 처리는 어디에도 없음.
- 탈퇴 신청 회원의 공개 읽기(GET /) — P-12가 "모든 요청"이라 읽기도 복구 화면으로 가는지 표에 명시 없음(본 매트릭스는 `W`로 해석).
