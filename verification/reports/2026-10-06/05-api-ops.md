### [높음] H1. CSP(12 §8)가 문서에 적힌 브라우저 동작 세 가지를 막는다 — 사진 직접 업로드·오프라인 사진 표시·소셜 사진 복사

- **문제:** CSP는 `default-src 'self'; script-src 'self'; img-src 'self' {CDN} data:; …`(12:149)이고 `connect-src`가 없으므로 `fetch`/XHR는 `'self'`로만 갈 수 있다. 그런데
  1. 04:271 "[브라우저 → S3] 원본·썸네일을 각각 업로드" — 23:56이 저장소에 "우리 사이트 출처(origin)에서 `PUT`만" CORS를 연다는 것 자체가 **다른 출처로의 PUT**이라는 뜻이다.
  2. 04:312 "화면에는 `URL.createObjectURL(blob)`로 정상 표시" — `img-src`에 `blob:`이 없다.
  3. 11:91 "[브라우저] 소셜 사진을 받음 (crossOrigin="anonymous", 5초 제한)"·11:89 미리보기 — `lh3.googleusercontent.com`, `avatars.githubusercontent.com`(11:100)이 `img-src`·`connect-src`에 없다.
- **영향:** 12 §11-7 "응답에 §8의 보안 헤더가 있다"를 지키는 순간 C-IMG-1(Tier B 공통) 사진 업로드가 브라우저에서 차단돼 동작하지 않는다. 오프라인 대기 사진은 깨진 그림으로 보이고, 소셜 사진 복사는 "조용히 기본 이미지로"(11:94) 떨어져 항상 실패한다.
- **제안:** 12 §8에 `connect-src 'self' {STORAGE_ORIGIN}`, `img-src`에 `blob:` 추가. 소셜 사진은 (a) 가입 마무리 화면에만 두 호스트를 더한 CSP를 쓰거나 (b) `connect-src`에 두 호스트를 넣고 `fetch` → Blob으로 처리. `{CDN}`·`{STORAGE_ORIGIN}`을 설정값으로 정의(부록 G).
- **담당:** 공통(12, 04, 11) · 강성찬(23 CORS와 맞춤)
- **확신:** 확실

### [높음] H2. `noeviction` Redis 하나에 캐시·세션·집계 키가 함께 들어간다 — 메모리 한도·분리 규칙이 없다 (D4)

- **위치:** docs/02-architecture.md:59, docs/07-auth.md:123, docs/02-architecture.md:191, docs/31-view-count.md:207, docs/04-draft-and-image.md:169, docs/32-trending.md:115, docs/05-publish.md:119, docs/21-comment.md:135, docs/21-comment.md:139, docs/30-like.md:147, docs/43-report-hide.md:26, docs/34-ai-tag-suggest.md:45

- **제안:** 02 §2(또는 새 §8 운영)에 ① Redis 고가용성(복제 + Sentinel 또는 관리형) 여부 ② 기능별 Redis 장애 정책 표(아래 D3 표를 초안으로: 세션 — 로그인 사용자 오류 허용 범위 / 요청 제한·중복 방지 — 통과 / AI — 503)를 두고, 31 §10-3은 "비회원 기준"으로 좁히거나 세션 조회 실패 시 비로그인으로 처리하는 필터를 정한다.

- **확신:** 확실 (규칙 없음) — 피해 형태는 프록시 설정에 따름

### [중간] M2. Redis 자동 저장 키가 DB보다 오래된 경우를 확인하지 않는다 — 장애 복구·발행 직후 409 반복, 옛 작업본 부활
- **위치:** docs/04-draft-and-image.md:101-102, docs/04-draft-and-image.md:108-115, docs/04-draft-and-image.md:136-142, docs/04-draft-and-image.md:169, docs/05-publish.md:134, docs/05-publish.md:147, docs/05-publish.md:150
- **문제:** 자동 저장 Lua는 Redis에 키가 있으면 그 버전만 기준으로 삼고 DB 버전은 "키가 없으면"만 쓴다(04:108-114). 그런데 ① Redis 장애 중에는 DB에 직접 써서 `edit_version`이 오르고(04:169), Redis가 돌아오면 옛 키(낮은 버전, TTL 24시간)가 남는다. ② 발행 후 키 삭제(05:150)는 커밋 후 별도 단계라 Redis 실패 시 남는다. ③ DB 반영 배치의 발행 글 경로(04:136-141)는 `post_draft.edit_version`과만 비교하는데, 발행이 `post_draft`를 지운 직후(05:147)에는 비교할 행이 없어 배치가 미리 읽어 둔 옛 버전이 그대로 INSERT된다. 발행(05:134)만 `max(Redis, post_draft, post)`를 쓴다.
- **영향:** ①②: 다음 자동 저장이 매번 409가 되고 비교 창의 "저장된 내용"에 옛 내용이 나온다 — [저장된 내용 불러오기]를 누르면 옛 글로 되돌아간다. ③: 발행 직후 글이 다시 "수정 중"이 되고, 에디터를 열면 발행본보다 오래된 작업본을 불러온다(04:155).
- **제안:** Lua 기준 버전을 `max(Redis 버전, ARGV[3] DB 버전)`으로 하고 Redis가 낮으면 키를 버린다(또는 장애 복구 시 DB에 직접 저장한 글의 키를 지우는 규칙). 04 §2-4 ②-b에 `AND :version > (SELECT edit_version FROM post WHERE id = :postId)` 조건 추가. 05 §7 ⑨ 실패 시 재시도할지 TTL에 맡길지 명시.
- **담당:** 공통(04, 05)

## 확인했지만 문제 없던 것
- 좋아요·팔로우가 같은 상태 지정 방식(`PUT`/`DELETE`, 이미 그 상태여도 200)이고 동시 요청에서 행·이벤트가 한 번(30 §4, 24 §4, 20 EV-4).
- 카드 목록 9(+1)·한 줄 목록 20이 같은 종류끼리 일관(10·22·24·32·33 / 13·21·24·25·41).
- 반응 수는 이벤트가 아니라 같은 트랜잭션에서 증감(03 E-6, 20 EV-6, 21 §5, 30 §4) — 이벤트 유실과 무관.
- 1분 작업 2개(04 자동 저장 반영, 31 조회수 반영)는 두 번 실행돼도 결과가 같다(버전 조건, `RENAME`·글별 `HDEL`). 단 M2의 발행 직후 경합은 별도.
- 탈퇴 정리 단계 순서(44 §4: 글 → 댓글 → 좋아요 → 사진 → 로그인 수단 → 친구 → 팔로우 → 알림 → 신고 → 회원)가 13 §3-3·21 §11·24 §6·25 §8과 일치하고 회원 1명 1트랜잭션.
- 비밀값은 환경 변수로만(02:177, 23:52, 34:67·314).
- 스크립트를 우리 서버 파일로 제공해 CSP `script-src 'self'`를 지킴(40 §4, 23 §5-2, 45 T-5).
- 글 상세 `Cache-Control: private`(40 R-9)로 사람마다 다른 화면이 공유 캐시에 들어가지 않음.
- 저장소 버킷 익명 목록 금지·파일 읽기만 공개·CORS는 PUT만(23 §2-2).
- 알림 폴링(30초, 탭이 가려지면 멈춤)은 서버 대수와 무관(25 NT-1).
- 태그 주소 인코딩·Spring 방화벽 검토(22 §5-1).
- 내 것 API와 알림 API에 회원 ID가 없음(11 §5, 41 M-2, 42 §10-3).
- 05 발행의 Redis 장애 시 대체(행 잠금 + 버전 확인, 05:119)와 31 조회 기록 건너뛰기(31:117)는 설계대로 성립.
- `00-scripts.txt`: 첫 실행은 6개 스크립트 모두 PASS였고, 15:04 재실행은 check-ddl §9 제안 적용만 FAIL(PASS 53 / FAIL 1, M6). 그 밖의 결과는 다시 확인하지 않았다.
