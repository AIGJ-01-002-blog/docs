# 3. 권한·보안·개인정보 검증 팀원 (권장 모델: Opus 5.5, effort high)

먼저 `verification/prompts/common.md`를 읽고 따른다. 보고서: `verification/reports/{날짜}/03-security-privacy.md`

## 임무

권한 규칙과 보안·개인정보 요구가 **모든 기능에 빠짐없이, 같은 방식으로** 적용됐는지 확인한다.

## 방법

1. **통합 권한 매트릭스**를 만든다: 행 = 모든 API·행동(문서에 나온 것 전부), 열 = 보는 사람(비회원 / 이메일 인증 전 회원 / 회원 / 작성자 / 친구(규격 적용 시) / 관리자 / 탈퇴 신청 회원), 칸 = 허용 / 401 / 403 / 404 / 429.
2. 칸마다 근거 문서를 적는다. **근거가 없는 칸**과 **문서끼리 다른 칸**을 보고한다.
3. 나민서의 C-OWN-1 권한 매트릭스와 비교한다.

## 확인할 것

| # | 항목 | 기준 |
|---|---|---|
| 1 | 404 원칙 | 볼 수 없는 리소스는 403이 아니라 404 (06 V-5). 판정 순서가 "볼 수 있는지 → 그 다음 조건"인지 (30 §2 예) |
| 2 | 리소스 상태별 | 임시글·비공개·친구 공개·휴지통·관리자 숨김·탈퇴 신청 작성자의 글에 대해 **모든 API**(상세, 목록, 검색, 트렌딩, 좋아요, 조회 기록, 댓글, 알림 링크, AI 추천)가 같은 결과인지 |
| 3 | XSS | 사용자 입력이 화면에 나오는 **모든 곳**: 본문(12), 제목, 소개, 닉네임, 댓글, 검색 강조(`<mark>`, 33 §5), 알림 문구, 링크 미리보기(OG), 404 안내 페이지. 각각 이스케이프·정화 규칙이 적혀 있는지 |
| 4 | CSRF | 상태를 바꾸는 모든 요청. 특히 비회원도 보내는 요청(조회 기록 31)과 `fetch keepalive` |
| 5 | 요청 횟수 제한 | 쓰기·외부 호출·검색 API마다 제한이 있는지. 키(회원/방문자/IP)와 수치를 표로 |
| 6 | 존재 노출 | 응답 차이로 가입 여부·비공개 글 존재·친구 관계를 알 수 있는 곳 (오류 메시지, 응답 코드, 응답 시간, 중복 확인 API) |
| 7 | 외부 전송 | AI(34)로 보내는 내용과 동의 문구가 정확한지 (Gemini 무료 등급은 Google이 개선에 사용·사람 검토 가능). 34 미결 제안 F-1(비공개 글은 Ollama만)의 위험을 평가 |
| 8 | 개인정보 저장 | IP·이메일·방문자 쿠키·검색어·글 내용이 DB·Redis·로그 중 어디에 얼마나 남는지 표로. 문서의 "남기지 않는다"와 맞는지 |
| 9 | 탈퇴 | 30일 뒤 익명 처리(13 §3-3) 후 개인을 알아볼 수 있는 데이터가 남는 곳이 없는지 (새 기능의 테이블·Redis 키 포함) |
| 10 | 비밀값 | API 키·OAuth 비밀값·SMTP 비밀번호가 환경 변수로만 주입되는지, 로그 규칙이 있는지 |
| 11 | 관리자 | 관리자가 할 수 있는 것과 없는 것(내용 수정 불가, 비공개 글 열람 불가 등)이 모든 문서에서 같은지 |

`scripts/sanitize/run.sh`가 이미 확인하는 것(본문 정화 XSS 32개)은 다시 하지 않는다. 대신 **본문이 아닌 출력 지점**에 집중한다.

## 인증·인가 빈틈 점검표 (2026-10-06 추가)

아래 항목마다 **문서에 답이 있는지(위치) / 없는지**를 표로 만든다. 없는 항목은 "문서 어디에도 없는 것"에 넣고, 있지만 모순되면 발견 사항에 넣는다.

| # | 항목 | 확인할 질문 |
|---|---|---|
| A1 | 관리자 지정 | `member.role = 'ADMIN'`은 누가 어떻게 부여하나? 첫 관리자는 어떻게 생기나? 관리자 계정 탈취 시 피해 범위는? |
| A2 | 정지 계정 | `status = 'SUSPENDED'`는 어떤 기능(43)이 만들고, 정지된 사람은 로그인·읽기·쓰기 중 무엇이 되는가? 정지 중 세션은 끊기나? |
| A3 | 탈퇴 신청 계정 | 유예 중 로그인하면 복구 화면만(13·44). 그 상태에서 API를 직접 호출하면? 세션이 남아 있으면? |
| A4 | 이메일 인증 강제 지점 | "인증 전 쓰기 불가"를 어디서 판정하나(필터? 서비스?). 소셜 가입은 인증된 것으로 보나? 인증 전 계정의 블로그 주소는 노출되나? |
| A5 | OAuth 보안 | `state`·PKCE, 콜백 주소 고정, 소셜 쪽 이메일 미인증 처리, 가입 마무리 전 세션(10분)의 보호 |
| A6 | 세션·토큰 | 세션 고정 방지, 동시 세션 수, 비밀번호 변경·탈퇴·정지 시 모든 세션 무효화, 쿠키 속성. **Q2(SSR+세션 vs REST+JWT)가 미결이면 양쪽 모두 성립하는지** |
| A7 | 로그인 보호 | 5회 실패 잠금을 계정이 아닌 IP·방문자 키로 우회할 수 있나? 잠금이 다른 사람의 로그인을 막는 DoS가 되나? 비밀번호 재설정 토큰의 1회성·만료 |
| A8 | 권한 판정 위치 | 모든 쓰기 API가 Service에서 소유자·상태를 다시 확인하나? 화면에서 숨긴 것만으로 막은 곳은 없나? (02·06·42) |
| A9 | 404 vs 403의 경계 | 볼 수 없는 리소스는 404(06 V-5). 그런데 "내 글인데 상태 때문에 못 하는 것"(휴지통 글 수정 등)은 404/409/403 중 무엇인가, 문서마다 같은가 |
| A10 | 리소스별 인가 | 사진(Presigned 업로드·열람), 작업본(`post_draft`), 임시글, 알림(남의 알림 읽음 처리), 댓글 수정·삭제(블로그 주인 권한?), 신고(자기 글 신고), 팔로우(차단?) |
| A11 | 관리자 권한 범위 | 관리자가 할 수 있는 것·없는 것(내용 수정 불가, 비공개 글 열람 불가)이 42·43·06에서 같은가. 관리자 행동의 기록(감사 로그)은 있나 |
| A12 | 요청 제한 키 | 방문자 키·IP를 `X-Forwarded-For`로 속일 수 있나? 프록시 뒤에서 실제 IP를 어떻게 얻나 |
| A13 | CSRF·CORS | SSR 폼, `fetch keepalive`(31), 비회원 요청(조회 기록), REST+JWT일 때 CORS 허용 출처 |
| A14 | 외부 링크·리다이렉트 | 로그인 후 복귀 주소(07 D-14) 검증, 본문 링크 `rel`(12), 소셜 사진 주소 허용 호스트(11) |
| A15 | 개인정보 권리 | 열람·정정·삭제 요청, 탈퇴 후 백업에 남는 데이터, 로그 보관 기간, 처리방침에 적을 항목 목록 |
