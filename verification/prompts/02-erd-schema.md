# 2. ERD·스키마 검증 팀원 (권장 모델: Opus 5.5, effort high)

먼저 `verification/prompts/common.md`를 읽고 따른다. 보고서: `verification/reports/{날짜}/02-erd-schema.md`

## 임무

모든 문서의 **ERD 변경 제안을 합친 통합 스키마**가 실제 PostgreSQL에서 적용되고, 문서의 규칙과 맞는지 확인한다.

## 방법

1. `scripts/check-ddl.sh`를 실행한다. 결과를 보고서에 붙인다.
2. 담당자 문서(20~49)의 "ERD 변경 제안"을 모두 모은다. **SQL 블록이 아닌 글로만 적힌 제안**(예: "컬럼 추가")도 표로 정리한다.
3. **임시 파일**에 통합 스키마를 만든다: `docs/03-erd.md`의 DDL + 06 친구 공개 규격 + 모든 제안. (`docs/`는 고치지 않는다. `/tmp/` 등에 만든다.)
4. 통합 스키마를 PostgreSQL 18에 적용한다. `scripts/lib/common.sh`의 `start_pg`·`qf`를 쓰거나 `docker run postgres:18`. **끝나면 컨테이너와 볼륨을 지운다** (`docker rm -f -v`).
5. 아래 항목을 확인한다.

## 확인할 것

| # | 항목 | 방법 |
|---|---|---|
| 1 | 통합 스키마 적용 | 순서 문제(FK가 아직 없는 테이블 참조), 이름 충돌, 같은 테이블에 대한 두 제안의 충돌 |
| 2 | 상태·종류 값 목록 | `visibility`, `status`, `image.purpose`, 신고 상태, 알림 종류 등 CHECK의 값 목록이 문서에 나온 모든 값을 포함하는지 |
| 3 | 삭제 규칙 | 각 FK의 `ON DELETE`가 13 문서의 휴지통·완전 삭제·탈퇴 익명 처리 순서와 맞는지. 새 테이블(알림·팔로우·신고 등)이 글 완전 삭제·회원 익명 처리 때 어떻게 되는지 |
| 4 | 목록 쿼리와 인덱스 | 문서에 나온 **모든 목록·검색 쿼리**를 모아 샘플 데이터(수천 행)로 `EXPLAIN`을 돌려, 정렬·필터에 맞는 인덱스가 있는지. 없으면 제안 |
| 5 | NULL 규칙 | NOT NULL·기본값이 문서의 "필수/선택"과 맞는지 |
| 6 | 이름 규칙 | 03에서 쓰는 규칙(테이블 단수형, 제약조건 `uq_`·`ck_`·`fk_`, 인덱스 `ix_`)을 새 테이블·제안도 따르는지. 이름 없는 제약조건이 섞여 있으면 정리할지 제안 |
| 7 | 비정규화 카운터 | `like_count`·`comment_count`·`view_count` 등을 바꾸는 모든 경로(생성·삭제·숨김·탈퇴)가 문서에 있는지 |
| 8 | Redis와 테이블의 경계 | 문서가 "Redis에 둔다"고 한 데이터를 테이블에도 만들거나, 그 반대인 곳 |

결과에는 **실행한 명령과 출력**을 함께 적는다. 실행하지 못한 확인은 "미실행"으로 표시한다.
