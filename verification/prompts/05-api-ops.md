# 5. API·운영 일관성 검증 팀원 (권장 모델: Opus 5.5, effort high)

먼저 `verification/prompts/common.md`를 읽고 따른다. 보고서: `verification/reports/{날짜}/05-api-ops.md`

## 임무

문서에 흩어진 **API, 오류 코드, Redis 키, 배치 작업, 설정값**을 표 하나씩으로 모으고, 서로 다르거나 충돌하는 곳을 찾는다. 이 표들은 다음 단계(#5 API 명세)의 초안이 된다.

## 만들 표 (보고서 부록에 전부 싣는다)

| 표 | 열 |
|---|---|
| **API 목록** | 메서드, 경로, 인증(비회원/회원/작성자/관리자), 요청, 성공 응답, 오류 응답(코드+이름), 요청 제한, 근거 문서 |
| **오류 코드** | 이름(예: `VERSION_CONFLICT`), HTTP 상태, 의미, 쓰는 API, 근거 문서 |
| **Redis 키** | 키 패턴, 값 형식, TTL, 쓰는 기능, 근거 문서 |
| **배치·스케줄 작업** | 이름, 주기·시각, 하는 일, 잠금(ShedLock), 실패 시, 근거 문서 |
| **설정값** | 키(`blog.…`), 기본값, 의미, 근거 문서 |
| **이벤트** | 이름, 필드, 발행 시점(커밋 후?), 구독자 |

## 확인할 것

| # | 항목 | 기준 |
|---|---|---|
| 1 | 경로 규칙 | `/api/me/…`, `/api/posts/{id}/…`, `/api/members/{handle}/…` 등 같은 종류의 리소스를 다른 규칙으로 부르는 곳. 복수형·동사 사용 |
| 2 | 상태 지정 vs 토글 | 좋아요(30)는 `PUT`/`DELETE`. 북마크·팔로우 등 비슷한 기능이 같은 방식인지 |
| 3 | 오류 응답 형식 | `{ code, errors: [{ field, code, message }] }` 형식을 모든 문서가 따르는지. 같은 상황에 다른 상태 코드(409 vs 400 vs 422)를 쓰는 곳 |
| 4 | 커서 형식 | 목록마다 커서 형식이 다른 곳 (`시각:id`, Base64, 스냅샷, 단계 포함). 통일할 수 있는지 제안 |
| 5 | 페이지 크기 | 9 / 20 / 100 등이 같은 종류의 목록에 섞여 있는지 |
| 6 | Redis 키 충돌 | 같은 접두어를 다른 의미로 쓰는 곳, TTL이 없는 키, 메모리 정책(04: `noeviction`)과 캐시 키(34)의 충돌 |
| 7 | 배치 시각 겹침 | 새벽에 도는 작업들(휴지통 비우기, 사진 정리, 조회수 보관, 좋아요 보정, 탈퇴 처리, 빈 임시글 정리 등)이 같은 시각에 몰리는지, 서로 순서가 필요한지 |
| 8 | 설정값 이름 | `blog.…` 접두어 규칙, 같은 의미의 다른 이름 |
| 9 | 이벤트 발행 시점 | 모두 커밋 후(`AFTER_COMMIT`)인지, 실패 시 유실 허용 여부가 적혀 있는지 |
| 10 | SSR/REST | 01 Q2(화면 구성)가 아직 미결이면, 문서의 API가 두 방식 모두에서 성립하는지 |

## 배포 점검표 (2026-10-06 추가)

문서의 설계를 **실제 운영 환경에 올린다고 가정**하고 아래를 확인한다. 답이 문서에 있으면 위치를, 없으면 "문서 어디에도 없는 것"에 넣는다.

| # | 항목 | 확인할 질문 |
|---|---|---|
| D1 | 구성 요소 목록 | 앱, PostgreSQL, Redis, 파일 저장소(SeaweedFS?), Ollama, 메일(Mailpit/SMTP), CDN — 각각 공통 필수인지 선택인지, 없으면 어떤 기능이 꺼지는지 |
| D2 | 서버 2대 | 세션(Redis), 자동 저장 버퍼, 스케줄러 잠금(ShedLock), 업로드 파일, 요청 제한 카운터, 트렌딩 스냅샷 — 모두 서버 밖에 있는가 |
| D3 | Redis 장애 | 기능마다 "Redis가 없으면 어떻게 되는지"가 적혀 있는가 (자동 저장 04, 조회수 31, 트렌딩 32, AI 캐시 34, 세션 07, 요청 제한). 서로 모순되거나 빠진 기능 |
| D4 | 메모리 정책 충돌 | 04는 `noeviction`(자동 저장 보호), 34는 캐시로 사용. 한 Redis에 같이 두면 캐시가 메모리를 채웠을 때 자동 저장 쓰기가 실패한다 — 분리할지, 키별 TTL로 막을지 |
| D5 | 스키마 변경 | Flyway 마이그레이션 순서(공통 V1 → 개인 확장), `CREATE EXTENSION pg_trgm` 권한, 이미 커밋한 마이그레이션 수정 금지, 개인 확장끼리 번호 충돌 |
| D6 | 배치 작업 | 모든 배치의 목록·시각·순서 의존(탈퇴 처리 → 사진 정리 등), 한 서버에서만(ShedLock), 실패 알림 |
| D7 | 환경 변수·비밀값 | 필요한 환경 변수 전체 목록이 어디에도 모여 있지 않다면 만든다 |
| D8 | 시간대 | DB 저장 기준(UTC/KST)과 "한국 시간 날짜" 배치·집계가 서버 시간대 설정에 의존하는지 |
| D9 | 상태 확인·관측 | 헬스체크(DB·Redis 포함), 요청 ID, 느린 쿼리 로그, 오류율 — 문서(02 §11, 김민서 OBS)에 있는 수준 |
| D10 | 백업·복구 | DB·파일 저장소 백업, 복구 절차 연습(김민서 REL-5) |
| D11 | 정적 자원·CSP | highlight.js·에디터 라이브러리를 우리 서버에서 제공(12 §8), CDN 주소가 CSP `img-src`와 맞는지 |
| D12 | 용량 성장 | `notification`, `post_view_daily`, `comment`, `image`, Redis 키 — 보관·정리 정책이 없는 테이블 |
