# 4. 완결성·측정 가능성 검증 팀원 (권장 모델: Opus 5.5, effort high)

먼저 `verification/prompts/common.md`를 읽고 따른다. 보고서: `verification/reports/{날짜}/04-completeness.md`

## 임무

모든 요구사항이 **구현할 수 있을 만큼 정해졌는지**, 완료 기준이 **테스트로 확인할 수 있는 문장인지** 확인하고, 남은 미결 사항을 한곳에 모은다.

## 방법

1. `docs/01-common-requirements.md`의 Tier A·B·C 표와 개인 확장 표에서 기능 목록을 만든다. 담당자 문서에 새로 생긴 기능도 더한다.
2. 기능마다 아래 체크리스트를 채운 **추적표**를 만든다.

| 기능 ID | 상세 문서 | 결정 표 | 완료 기준 | API | 화면 상태(빈·오류·로딩) | ERD 영향 | 이벤트·알림 | 미결 |
|---|---|---|---|---|---|---|---|---|

3. 빈 칸이 있는 기능, 아래 기준에 맞지 않는 완료 기준을 보고한다.

## 완료 기준을 판단하는 법

| 좋은 완료 기준 | 나쁜 완료 기준 |
|---|---|
| "같은 요청을 동시에 20번 보내도 1건이다" | "중복이 없어야 한다" (어떻게 확인?) |
| "글 10만 개에서 p95 500ms 이하" | "빨라야 한다" |
| "남의 글 수정 요청은 404이고 글은 바뀌지 않는다" | "권한을 잘 확인한다" |

기준: **입력·조작 → 관찰할 결과**가 있고, 자동 테스트로 만들 수 있는가.

## 함께 모을 것

| # | 목록 | 찾는 곳 |
|---|---|---|
| 1 | **미결 사항** | `미결`, `후속 제안`, `[질문]`, `확인 필요`, `팀`이 결정할 것, "다시 재야 한다"(측정 필요) |
| 2 | **맞추기로 한 것의 상태** | 각 문서의 "다른 담당자와 맞출 것" 항목 → 상대 문서에 반영됨 / 안 됨 / 확인 불가 |
| 3 | **배포 환경에 달린 것** | 저장소 제품, Ollama 서버 자원, `pg_trgm` 권한, 메일 발송, 도메인 등 |
| 4 | **측정이 필요한 것** | 문서가 "측정 결과는 예시 데이터 기준"이라고 한 곳 |

이 네 목록은 화요일 이후 할 일 목록이 되므로 **빠짐없이** 모은다.

## 블로그 서비스에 흔히 필요한데 문서에 없을 수 있는 것 (2026-10-06 추가)

추적표를 만든 뒤, 아래 주제가 **어느 문서에라도 있는지** 확인하고 없는 것은 "문서 어디에도 없는 것"에 넣는다. 공통 범위 밖이라고 결정된 것(01 Tier C·개인 확장)은 제외한다.

| 분류 | 주제 |
|---|---|
| 계정 | 첫 관리자 생성, 정지 계정의 경험, 이메일 변경 불가 안내, 로그인 수단을 잊은 사용자 안내(07 §4-1 외), 동시 로그인 |
| 콘텐츠 | 글 주소 공유 시 OG 이미지 기본값, 404·500 페이지, 글이 0개인 홈, 매우 긴 제목·태그의 화면 처리, 코드 블록 가로 스크롤(모바일) |
| 탐색 | sitemap·robots·RSS(김민서 SHARE-1은 개인 확장인데 SEO 비기능 요구에는 sitemap이 있음), 홈 첫 화면에서 트렌딩·최신 외에 필요한 것 |
| 운영 | 백업·복구, 로그 보관, 장애 안내 페이지, 운영자 연락처, 약관·개인정보 처리방침 페이지 자체(동의는 받는데 문서는 어디에?), 서비스 이름 확정(08 예약어) |
| 시간·언어 | 모든 시각의 기준(KST 저장 vs UTC 저장 + KST 표시), 날짜 경계(트렌딩·조회수·보관 배치), 한국어 외 입력 |
| 접근성·화면 | 키보드 조작, 색 대비, 폼 오류 안내 — 문서에 흩어진 규칙이 공통 원칙으로 모여 있는가 |
| 품질 | 통합 테스트 범위(권한 매트릭스 자동 테스트는 있음), 성능 측정을 다시 할 시점과 기준 데이터 |
