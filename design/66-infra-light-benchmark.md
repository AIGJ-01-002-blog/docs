# 지금 구성과 가벼운 구성 실측 비교

작성 2026-10-13 · 이슈 devlog#172 (목표 #169) · 측정 코드 devlog `deploy/bench/`, `deploy/scripts/infra-bench-prod.sh`

강사님 피드백(민서님 전달, 2026-10-13): "서버 도커 이미지 위에 쿠버네티스 도커 이미지랑 그 위에 내 서버 이미지와 인프라 이미지들 때문에 느리다".

## 1. 결론

- **쿠버네티스 층은 요청을 느리게 만들지 않는다.** 운영 서버 안에서 nginx 인그레스·kube-proxy를 거쳐도 앱만 부를 때보다 1~2ms 더 걸린다. 같은 러너에서 Compose와 비교해도 한 번에 하나씩 부를 때 2ms 차이다.
- **느린 곳은 한국 → Cloudflare 구간이다.** 같은 학교 서버에서 `www.cloudflare.com`은 서울(ICN) Cloudflare에 8ms로 붙는데 `devlog.life`는 홍콩(HKG)·도쿄(NRT) Cloudflare로 가서 연결 한 번에 45~260ms가 걸린다. 새 연결은 왕복을 서너 번 하므로 공개 주소 응답이 0.3~1.1초가 된다. 무료 요금제 주소를 한국 통신사가 해외 지점으로 보내는 것으로 보이며, 이 원인은 추정이다.
- **겹겹 구성의 진짜 비용은 메모리·CPU·기동 시간이다.** 쿠버네티스 자체가 약 1.6GB를 더 쓰고, 기동이 5배 느리고, 동시 요청 처리량은 같은 4코어에서 절반 이하다. 가장 큰 자원은 쿠버네티스가 아니라 Ollama 임베딩(3.0GB, CPU 1.4코어)이다.

## 2. 측정 방법

| 측정 | 어디서 | 무엇을 |
|---|---|---|
| 운영 실측 | 학교 서버(16코어·128GB, 컨테이너 79개를 여러 학생이 같이 씀). GitHub Actions "운영 구성 측정"이 SSH로 들어가 읽기만 함 | docker stats, kubectl top, 노드 프로세스별 RSS, 단계별 curl 30번 |
| 같은 기계 비교 | GitHub 러너(4코어·16GB). "구성 비교 측정"이 두 구성을 차례로 띄움 | 같은 앱 이미지와 같은 PostgreSQL·Redis·MinIO 이미지. 한 번에 하나 200번, 동시 20개 2000건(ab) |
| 바깥 | 미국 러너, 미국 작업 환경 | 공개 주소 첫 바이트 시간 |

운영 사이트 설정은 아무것도 바꾸지 않았다(민서님 허락, 2026-10-13).

## 3. 운영 서버: 요청이 거치는 단계별 시간

ms, 30번 중앙값(p50). 두 번 잰 값의 범위.

| 요청 | ① 앱만 (파드 안) | ② 서비스(kube-proxy) → 앱 | ③ nginx 인그레스 → 앱 | ④ 서버에서 공개 주소로 |
|---|---|---|---|---|
| `/api/auth/me` (로그인 확인) | 0.6~0.9 | 1.5~2.1 | 1.0~1.6 | 694~1,085 |
| `/api/members/kim755030/posts` | 3.5~4.5 | 5.0~5.6 | 4.1~4.6 | 271~864 |
| `/@kim755030` (블로그 화면) | 8.5~9.9 | 10.0~10.4 | 7.3~9.5 | 551~888 |
| 사진 썸네일 (MinIO) | - | - | 1.3~1.4 | 257~1,045 (Cloudflare 캐시) |
| `favicon.svg` (Cloudflare 캐시) | - | - | - | 428~649 |

④에서 ③을 빼면 0.3~1초가 서버 바깥에서 생긴다. Cloudflare에 캐시돼 서버까지 오지도 않는 favicon도 0.4~0.6초 걸린다.

### 서버 ↔ Cloudflare 구간

| 주소 | 붙는 Cloudflare | TCP 연결 | TLS까지 | 전체 |
|---|---|---|---|---|
| `www.cloudflare.com` | ICN(서울) | 8~10ms | 56~70ms | 65~80ms |
| `devlog.life/favicon.svg` | HKG(홍콩)·NRT(도쿄), 잴 때마다 바뀜 | 45~260ms | 284~572ms | 413~851ms |
| `devlog.life/api/auth/me` | 같음 | 190~259ms | 440~579ms | 852~1,110ms |
| `www.google.com` | - | 33~35ms | 119~124ms | 151~157ms |

터널(cloudflared)은 ICN·FUK(후쿠오카)에 붙어 있다. 그래서 한국 방문자 요청은 한국 → 홍콩·도쿄 Cloudflare → 서울 터널 → 학교 서버로 돈다.

## 4. 운영 서버: 자원

학교 서버의 내 노드 컨테이너(`k3d-devlog-server-0`, 상한 10GB): **6.1GB, CPU 2.7코어(최대)**.

| 무엇 | 메모리 | CPU | 쿠버네티스가 없어도 필요한가 |
|---|---|---|---|
| Ollama 임베딩(bge-m3, `llama-server`) | 2,850~3,040MiB | 1.2~1.4코어 | 검색 기능을 쓰면 필요 |
| 앱(Java) 2개 | 1,290~1,313MiB | 거의 0 | 1개면 650MiB |
| PostgreSQL | 70~346MiB | 거의 0 | 필요 |
| MinIO | 96~146MiB | 거의 0 | 필요 |
| Redis | 8~13MiB | 거의 0 | 필요 |
| cloudflared 2개 | 40~82MiB | 거의 0 | 1개면 충분 |
| **k3s(제어판·kubelet)** | **500MiB** | | 아니요 |
| **containerd + shim 14개** | **290MiB** | | 아니요 |
| **ingress-nginx** | **220~325MiB** | | 아니요(앱이 바로 받음) |
| **metrics-server·coredns·local-path·대시보드** | **약 190MiB** | | 아니요 |

굵게 쓴 쿠버네티스 몫이 **약 1.2~1.6GB**다. 공용 서버의 다른 컨테이너 78개는 합쳐서 약 39GB를 쓴다.

## 5. 같은 러너에서 두 구성 비교

GitHub 러너 4코어·16GB, 같은 앱 이미지(431MB). Ollama는 러너에서 임베딩 모델을 올리지 않아(요청이 없어서) 49MiB로 잡혔다. 운영처럼 모델이 올라가면 두 구성 모두 약 3GB를 더 쓴다.

| | 가벼운 구성 (Compose) | 지금 구성 (k3d) | 차이 |
|---|---|---|---|
| 부품 | 앱 1 + PostgreSQL + Redis + MinIO | k3s + ingress-nginx + 앱 2 + PostgreSQL + Redis + MinIO + Ollama + 시스템 파드 4 | |
| 기동(시작 → 응답) | **21~25초** | 110~152초 | 5배 |
| 쉬는 동안 메모리 | **571~585MiB** | 2,166~2,294MiB | +1.6GB |
| 응답 `/api/auth/me` p50 | **1.6ms** | 3.7ms (nginx 경유) | +2ms |
| 응답 `/api/posts` p50 | **2.2ms** | 4.1ms | +2ms |
| 동시 20개 처리량 `/api/auth/me` | **3,955~5,158건/초** | 1,617건/초 | 0.3~0.4배 |
| 동시 20개 처리량 `/api/posts` | **1,955~2,379건/초** | 762건/초 | 0.3~0.4배 |
| 동시 20개 p95 `/api/posts` | **17~24ms** | 51ms | |

처리량 차이는 4코어에서 k3s·nginx가 앱과 CPU를 나눠 쓰고, 요청이 nginx·kube-proxy를 한 번씩 더 지나기 때문이다. 학교 서버(16코어)에서는 CPU가 남아 차이가 작을 것이다. 지금 사이트 방문자 수는 이 처리량의 아주 일부라서 체감할 일은 없다.

## 6. 선택지와 추천

| 선택지 | 빨라지나 | 줄어드는 자원 | 일 | 잃는 것 |
|---|---|---|---|---|
| A. 그대로 둠 | 아니요 | 없음 | 없음 | - |
| B. Compose로 바꿈 (앱 1 + DB·Redis·MinIO·Ollama + cloudflared 1) | **아니요** (요청당 1~2ms) | 메모리 약 1.6GB, 기동 2분 → 20초 | 배포 스크립트·백업·롤백을 Compose로 다시 짬 | 무중단 배포(파드 2개 교대), 자동 롤백, 대시보드 |
| C. Ollama만 끄거나 필요할 때만 올림 (`OLLAMA_KEEP_ALIVE`를 짧게) | 아니요 | 메모리 약 3GB, CPU 1.4코어 | 설정 한 줄 | 검색 첫 요청이 모델 올리는 몇 초만큼 느려짐 |
| D. 한국 방문자가 서울 Cloudflare로 가게 함 | **예**, 공개 주소 0.3~1초 → 수십 ms로 기대 | 없음 | 요금제·경로 확인 필요 | 비용 가능성 |

**추천: D를 먼저 확인하고, 자원은 C로 줄인다. B(쿠버네티스 걷어 내기)는 속도 문제의 해법이 아니다.**

- 강사님이 느끼신 지연은 측정상 쿠버네티스 층이 아니라 한국 → 해외 Cloudflare 경로에서 생긴다. 쿠버네티스를 빼도 그 0.3~1초는 그대로 남는다.
- 다만 "서버 한 대에 쿠버네티스는 과하다"는 지적은 자원 면에서 맞다. 1.6GB와 2분 기동은 이 규모에서 얻는 것(파드 2개 무중단 배포)보다 비싸다. 다음 목표에서 B를 할지 정할 때 이 표를 근거로 쓴다.
- 발표에서는 "느린 이유를 층별로 재 보니 쿠버네티스는 1~2ms였고, 진짜 원인은 CDN 경로였다"가 강사님 지적에 숫자로 답하는 방법이다.
